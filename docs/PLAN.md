## TL;DR

- **Продукт:** один Telegram-бот — каталог тайтлов. Тайтл — это dating sim: сюжетные сцены плюс игровой цикл (время суток, энергия, занятия, предметы, характеристики, отношения, квесты). Поверх тайтлов — общий аккаунт: уровень, достижения, коллекция, премиум-валюта.
- **Главное архитектурное решение:** игровой цикл исполняет сервер, сцены — клиент.
  - Клиент присылает действие («пойти в спортзал вечером»), сервер проверяет условия, тратит энергию и время, применяет эффекты и говорит, какую сцену показать.
  - Всё, что стоит денег или может стоить, считается только на сервере.
- **Движок один на все тайтлы и настраивается данными.**
  - Время, ресурсы, характеристики, локации, занятия, предметы, квесты и события описываются в студии.
  - Новый тайтл не требует программиста, пока ему хватает возможностей движка. Новая механика добавляется в движок один раз и становится доступна всем тайтлам.
- **Сцены пишутся на [ink](https://github.com/inkle/ink)** плюс наши теги. Сцена читает состояние игры и возвращает эффекты, которые сервер применяет по белому списку.
- **Студия нужна, и её центр смещается:**
  - редакторы игровых данных с проверкой ссылок;
  - песочница — запуск с любым состоянием;
  - симулятор баланса;
  - а также, как раньше, редактор сцен с превью и публикация.
- **Стек:**
  - Python (FastAPI, aiogram, SQLAlchemy) — сервер и игровой движок;
  - TypeScript/React — плеер, студия, рендер сцен;
  - PostgreSQL на VPS в РФ;
  - арт и звук в Supabase Storage, раздаёт VPS.
- **Деньги:** цифровые товары в Telegram — только за Stars. Монетизация после MVP, но кошелёк и леджер проектируются сразу как общие для платформы.
- **Оценка:** команда — один разработчик и геймдизайнер, срок ~19 недель (этап 0 уже сделан). Со вторым разработчиком вышло бы ~11–12. Кроме геймдизайнера, для контента нужны сценарист и художник.

## 1. Продукт и границы MVP

### Что такое продукт
Платформа в одном боте: каталог тайтлов, общий профиль игрока, запуск тайтла прямо в Mini App. Тайтл — dating sim в вертикальном формате:
- **Сюжет:** сцены с фоном, спрайтами персонажей с эмоциями, диалоговым окном и выборами. Часть выборов платная.
- **Игровой цикл:**
  - день делится на слоты времени;
  - занятия в локациях тратят энергию и время, а дают характеристики, деньги, предметы и симпатию;
  - персонажи появляются по расписанию;
  - события срабатывают по условиям и запускают сцены;
  - квесты ведут игрока по сюжету.

Контент делает наша команда, пользовательского контента нет.

### Словарь
| Термин | Что это |
|---|---|
| Платформа | Бот + Mini App + общий аккаунт игрока |
| Тайтл (релиз) | Отдельная игра: свой мир, персонажи, данные, сцены и сохранение |
| Сцена | Фрагмент сюжета на ink: диалог, свидание, событие |
| Игровые данные | Описание тайтла для движка: время, ресурсы, локации, занятия, предметы, расписания, квесты, события, кривые прогрессии |
| Движок | Серверный код на Python, который исполняет правила по игровым данным |
| Сохранение | Состояние игрока в тайтле |
| Глобальный прогресс | Состояние аккаунта поверх тайтлов: уровень, достижения, коллекция, кошелёк |

### Входит в MVP
| Блок | Что именно |
|---|---|
| Платформа | Каталог тайтлов, профиль (уровень аккаунта, достижения, коллекция), запуск тайтла, диплинки на тайтл |
| Движок | Время суток и дни, ресурсы с восстановлением, характеристики, отношения, локации, занятия, расписания персонажей, предметы и инвентарь, квесты, события, условия и эффекты, сохранения на сервере |
| Сцены | ink → поток VN-команд (фон, персонаж, реплика, выбор, звук), чтение состояния игры, эффекты по белому списку |
| Студия | Тайтлы, ассеты, персонажи; редакторы игровых данных с проверкой ссылок и импортом таблиц; редактор сцен с превью; песочница; симулятор баланса; публикация и откат |
| Плеер (TMA) | Каталог и профиль; внутри тайтла — карта локаций, панель времени и ресурсов, занятия, сцены, инвентарь, журнал квестов, отношения |
| Инфраструктура | Прод + стейджинг, HTTPS, CI/CD, миграции, бэкапы, Sentry, аналитика |
| Контент | Вертикальный срез первого тайтла: 7 игровых дней, 4–5 локаций, 2 героя для романа, 6–8 занятий, 10–15 предметов, 3–5 квестов, 15–25 сцен |

### Не входит в MVP (осознанно)
- Оплата: кошелёк и леджер спроектированы, покупок нет.
- Магазины, крафт, гардероб и наряды.
- Мини-игры.
- Пуш-уведомления, рефералка, локализация.
- Сложные анимации: только fade и shake.

### Критерии готовности MVP
1. Геймдизайнер и сценарист без разработчика собирают тайтл: данные, сцены, арт. Они проверяют его в песочнице и публикуют.
2. Игрок открывает бота → каталог → тайтл и проходит игровую неделю: занятия, встречи по расписанию, события, квесты, сцены, инвентарь. Опыт аккаунта и достижения начисляются в профиль.
3. Всё, что меняет состояние, считает сервер. Повтор запроса или подделанный ответ клиента не дают лишних ресурсов.
4. Сохранение синхронизируется между устройствами. Публикация новой версии тайтла не ломает существующие сохранения (§4.5).
5. Прод работает на своём домене, деплой идёт по мерджу в `develop` (стейджинг) и `master` (прод), ночные бэкапы проверены восстановлением, ошибки видны в Sentry.

## 2. Ключевые решения

### 2.1 Платформа: один бот, много тайтлов, общий аккаунт
- Один бот и одно Mini App. Каталог тайтлов — главный экран, тайтл открывается внутри того же приложения.
- Диплинк `t.me/<bot>/<app>?startapp=title_<slug>` открывает сразу нужный тайтл: для рекламы, постов в канале и рефералки.
- У игрока один аккаунт: профиль, уровень, достижения, коллекция и кошелёк общие. Сохранения у каждого тайтла свои (§4.6).

### 2.2 Игровой цикл — на сервере, сцены — на клиенте
- **Сервер — единственный источник правды для состояния игры:** время, ресурсы, предметы, характеристики, отношения, квесты, валюты.
  - Энергия — основной товар таких игр, поэтому её нельзя считать на клиенте.
  - Правила реализованы один раз, на Python. На клиенте они не дублируются.
- **Клиент показывает то, что прислал сервер:** доступные действия с причинами блокировки, состояние, сцену для показа.
- **Сцены исполняются на клиенте**, чтобы между репликами не было сетевых задержек. Сцена получает состояние только для чтения и в конце возвращает эффекты (§5.3).
  - Сервер применяет только эффекты из белого списка, извлечённого из скомпилированной сцены при публикации.
  - Премиум-валюту и платные предметы сцены не выдают вообще — только серверные правила.
  - Если понадобится строгая проверка выборов, сервер сможет переигрывать сцену в Node-воркере (`inkjs` уже есть в образе API). Для MVP хватит белого списка.
- **Цена:** каждое игровое действие — это запрос к серверу. Для dating sim, где темп задаёт игрок, это не проблема.

### 2.3 Движок один на все тайтлы и настраивается данными
- Тайтл описывается данными (§4.1). Набор ресурсов, характеристик, слотов времени, правила восстановления энергии и всё остальное задаются в студии, а не в коде.
- Схемы данных пишутся один раз на Python (Pydantic). Из них автоматически получаются:
  - проверка при сохранении и публикации;
  - формы в студии (JSON Schema → генератор форм);
  - типы для плеера (через OpenAPI).

  Новая сущность — это новая схема, и форма для неё появляется без отдельной вёрстки.
- **Правило против расползания:** уникальная механика тайтла добавляется в движок как общая возможность, а не веткой «если тайтл X». Мини-игры в будущем подключаются как плагины-компоненты по ключу.
- Тот же Python-код движка работает в API, в песочнице студии и в симуляторе баланса. Симулятор проигрывает ровно те правила, что и прод.

### 2.4 Сцены: ink + теги
- **Почему ink.** Это проверенный язык (на нём сделаны 80 Days, Heaven's Vault и другие игры), он рассчитан на сценаристов. `inkjs` работает в браузере и в Node, умеет сохранять состояние, компилирует прямо в студии и поддерживает теги, в том числе на выборах.
- **Почему не свой граф-редактор.** Это отдельный продукт на месяцы. Структуру тайтла (квесты, события) и так описывают игровые данные, а ink остаётся для текста сцен.
- **Страховка от привязки к ink.** Движок сцен (`packages/engine`) отдаёт рендереру собственный поток команд, а рендерер про ink ничего не знает.

### 2.5 Монетизация: только Telegram Stars
- Правила Telegram требуют продавать цифровые товары и услуги в ботах и Mini App за Stars (валюта `XTR`).
- **Кошелёк — общий для платформы:**
  - премиум-валюта («кристаллы») покупается за Stars и тратится в любом тайтле;
  - деньги внутри тайтла остаются в сохранении тайтла.
- Что продаём — решаем после MVP. Типичные варианты: восполнение энергии, платные выборы, предметы и наряды, подписка (Stars поддерживают подписки).
- Флоу оплаты — §13.1.

### 2.6 Python для сервера и движка, TypeScript для сцен и интерфейсов
- **Python:** данные, пользователи, игровой движок, платежи, бот, обработка медиа, публикация, симулятор баланса.
- **TypeScript:** формат сцен (движок сцен, линтер, компилятор), рендер, плеер, студия.
- **Компилятора ink на Python нет.** При публикации API вызывает `node packages/engine/compile.mjs`: на вход исходники сцен и реестр ключей, на выход скомпилированные сцены, белые списки эффектов, ошибки. Это тот же код, что работает в превью студии. Версия `inkjs` зафиксирована в одном месте.
- **Типы между сервером и фронтендом** берутся из OpenAPI: FastAPI отдаёт схему, `openapi-typescript` генерирует клиент.

### 2.7 Аудитория в РФ: персональные данные — в России, арт — в Supabase
- **Всё, что касается пользователей, хранится в России:** API, PostgreSQL и бэкапы — на российском VPS и в российском S3 (152-ФЗ).
- **Supabase хранит только арт и звук** (бакеты `assets` и `originals`) через S3 API. Остальное в проекте Supabase закрыто (§10.4).
- **Игроки не обращаются к `*.supabase.co`.**
  - Воркер кладёт готовые варианты ассетов и в Supabase, и в локальную копию на VPS (`/srv/assets`).
  - Caddy раздаёт копию с домена приложения, поэтому CORS не нужен.
  - Опубликованный контент от Supabase не зависит.
- **CDN пока не нужен.** Подключается сменой `ASSETS_BASE_URL`, когда канал VPS перестанет справляться (§6.5).
- **План отступления:** код не завязан на Supabase. Переезд на российский S3 — это `rclone` и смена переменных окружения.

### 2.8 Студия — отдельный сайт, клиенты в базу напрямую не ходят
- Студия — веб-приложение на `studio.<домен>` для работы на компьютере. Плеер и студия ходят **только в наш API**, права разделяет API (тип входа + роль), RLS не используем.

|  | Плеер | Студия |
|---|---|---|
| Что это | Mini App в боте | Сайт `studio.<домен>` |
| Кто пользуется | Любой пользователь Telegram | Только команда (таблица `staff`) |
| Вход | `Authorization: tma <initData>` в каждом запросе | Telegram Login Widget или одноразовая ссылка из бота → cookie-сессия |
| Эндпоинты | `/api/*` | `/api/studio/*`, на каждом маршруте проверка роли |

- Подписи `initData` и Login Widget проверяются разными алгоритмами:
  - Mini App: `HMAC_SHA256(key="WebAppData", bot_token)`;
  - Login Widget: `SHA256(bot_token)`.
- Отдельный бот для студии не нужен. Запасной вход — команда `/studio`: бот присылает одноразовую ссылку тем, кто есть в `staff`.

## 3. Архитектура

```
  Telegram (телефон)                                 Команда (ПК)
 ┌─────────────────────────┐                      ┌─────────────────────────┐
 │ Бот ──► Mini App        │                      │ Studio (сайт)           │
 │ каталог · тайтл · сцены │                      │ данные · сцены · песочн.│
 └───────────┬─────────────┘                      └────────────┬────────────┘
             │ app.<домен>/api, initData                       │ studio.<домен>/api, cookie
             ▼                                                 ▼
   ┌─────────────────────────── VPS в РФ ────────────────────────────────────┐
   │ Caddy (HTTPS, статика, /api → api, /assets → копия)                     │
   │ api: платформа · игровой движок · публикация · бот · node compile.mjs   │
   │ worker: медиа, плановые задачи · PostgreSQL · /srv/assets               │
   └──────┬────────────────────────────┬────────────────────────────┬────────┘
          │ S3 API (boto3)             │ pg_dump, rclone            ▲ webhook
          ▼                            ▼                            │
   Supabase Storage (EU)        S3 в РФ: бакет backups        Telegram Bot API
   assets, originals            (дампы базы, копия originals)
```

### Слои
| Слой | Где исполняется | Что делает |
|---|---|---|
| Платформа | Сервер | Аккаунт, каталог, глобальный прогресс, кошелёк, покупки |
| Игровой движок | Сервер | Исполняет данные тайтла: действия, время, ресурсы, условия, эффекты, события, квесты |
| Сцены | Клиент (плеер, превью студии) | Исполняет ink, рисует сцену, собирает эффекты |
| Контент | Студия → сборки | Данные тайтла + скомпилированные сцены + манифест ассетов, неизменяемые версии |

### Структура репозитория
```
tg_app_storymaker/
├─ apps/
│  ├─ api/            # Python: API, бот, публикация, медиа
│  │  └─ src/storymaker_api/game/   # движок: схемы данных, условия, эффекты, действия, симулятор
│  ├─ player/         # TS/React — Mini App
│  └─ studio/         # TS/React — сайт студии
├─ packages/
│  ├─ engine/         # TS: сцены — inkjs → поток команд, линтер тегов, compile.mjs
│  ├─ vn-renderer/    # TS/React: рендер сцены (плеер и превью студии)
│  ├─ game-ui/        # TS/React: экраны тайтла (плеер и песочница студии)
│  └─ api-client/     # TS: сгенерирован из OpenAPI (включая схемы игровых данных)
├─ infra/  docs/  .github/
```

Общие пакеты — главная идея: превью и песочница в студии используют тот же код, что и плеер у игрока, а симулятор баланса — тот же движок, что и прод.

## 4. Игровая модель

### 4.1 Из чего состоит тайтл
| Сущность | Что описывает |
|---|---|
| Конфигурация | Слоты времени (например, утро, день, вечер, ночь), что происходит при смене дня, ресурсы (энергия, деньги) и правила их восстановления, характеристики, пороги отношений, стартовое состояние |
| Персонажи | Имя, спрайты и эмоции, предпочтения в подарках, уровни отношений |
| Расписания | Где персонаж находится в какой день и слот, с условиями |
| Локации | Фон, доступные слоты, условия открытия |
| Занятия | Локация, слоты, цена (энергия, время, деньги), требования, эффекты, связанные события |
| Предметы | Тип (подарок, расходник, ключевой), описание, иконка, эффекты использования |
| Квесты | Условия старта, этапы с целями-условиями, награды, тексты журнала |
| События | Где и когда проверяются, условия, приоритет, однократность, сцена, эффекты |
| Кривые | Опыт → уровень, пороги наград, таблицы баланса |

### 4.2 Время и ресурсы
**Решение для первого тайтла:**
- день делится на игровые слоты (например, утро, день, вечер, ночь), занятия сдвигают время, день заканчивается сном;
- энергия восстанавливается в реальном времени (+1 в N минут, до максимума);
- энергию можно восполнить за кристаллы, когда появится монетизация.

Это классическая схема жанра: игрок возвращается, когда энергия восстановилась, а время в игре идёт только тогда, когда он играет.

Движок при этом поддерживает обе модели, выбор делается в конфигурации тайтла, так что следующий тайтл может работать иначе:
- **Время:**
  - игровые слоты, которые сдвигаются действиями, а день заканчивается сном;
  - или привязка к реальному времени.
- **Ресурсы:**
  - восстановление в реальном времени (например, +1 энергии в N минут);
  - или при смене игрового дня;
  - или и то и другое.

Восстановление в реальном времени считается лениво. В сохранении хранятся значение и момент последнего обновления, и при каждом чтении сервер досчитывает прошедшее время. Фоновые таймеры не нужны.

### 4.3 Условия и эффекты
Условия и эффекты — это данные. Их понимают движок (исполнение), студия (проверка ссылок и подсказки) и симулятор. Пример занятия; в студии оно редактируется формой, YAML здесь только для наглядности:

```yaml
id: gym_workout
location: sports_center
slots: [morning, evening]
cost: { energy: 20, slots: 1 }
requires:
  stat.fitness: { lt: 100 }
effects:
  add: { stat.fitness: 3, global.xp: 5 }
events:
  - scene: anna_gym_meet
    when:
      affection.anna: { gte: 10 }
      flag.met_anna: true
    once: true
```

- **Пути состояния:**
  - `stat.*`, `resource.*`, `affection.<персонаж>`, `item.<предмет>`, `flag.*`, `quest.<квест>.stage`, `time.day`, `time.slot` — данные тайтла;
  - `global.*` — глобальный прогресс, только для чтения, кроме опыта и достижений.
- **Комбинаторы:** `any`, `not`, по умолчанию все условия должны выполниться.
- **Эффекты:** `add`, `set`, `give`, `take`, `start_quest`, `advance_quest`, `unlock`, `achievement`, `collect` (в коллекцию).

### 4.4 Цикл действия
1. Клиент: `POST /api/titles/{slug}/actions {type: "activity", id: "gym_workout", request_id}`.
2. Сервер в одной транзакции:
   - блокирует сохранение (`SELECT … FOR UPDATE`);
   - досчитывает восстановление ресурсов;
   - проверяет условия и цену;
   - списывает ресурсы и сдвигает время;
   - применяет эффекты;
   - выбирает событие с наивысшим приоритетом;
   - записывает действие в `action_log`.
3. Ответ: новое состояние, доступные действия с причинами блокировки, сцена для показа (если сработало событие), сводка изменений («+3 к форме»).
4. Клиент играет сцену и отправляет `POST /api/titles/{slug}/scenes/{key}/complete {request_id, effects, choices}`. Сервер применяет эффекты, которые есть в белом списке сцены, и проверяет квесты.

`request_id` уникален в рамках сохранения: повторный запрос (обрыв сети, двойной тап) возвращает уже записанный результат и ничего не применяет второй раз.

### 4.5 Сохранения и обновления контента
- Сохранение — JSONB в `saves`: состояние, `build_id` и `revision`.
- **Идентификаторы в данных стабильны.** Предметы, квесты, флаги и локации не удаляются, а помечаются устаревшими. Публикация не пройдёт, если новая сборка теряет идентификатор, на который могут ссылаться сохранения, без явного правила миграции (переименование или замена).
- При первом обращении после смены сборки сервер мигрирует сохранение по правилам из данных и запоминает новый `build_id`.
- Если сборка сменилась посреди сцены, сцена начинается заново. Сцены короткие, а их эффекты применяются только в конце.
- В песочнице у сотрудников отдельные сохранения (`slot = sandbox:*`), реальный прогресс они не трогают.

### 4.6 Глобальный прогресс
| Что | Где живёт | Пример |
|---|---|---|
| Премиум-валюта | Аккаунт | Кристаллы за Stars, тратятся в любом тайтле |
| Уровень и опыт аккаунта | Аккаунт | Опыт за занятия, квесты и концовки в любом тайтле |
| Достижения | Аккаунт; тайтловые помечены тайтлом | «Первое свидание», «Пройдено 3 тайтла» |
| Коллекция | Аккаунт | Открытые иллюстрации и концовки всех тайтлов |
| Время, энергия, деньги тайтла, инвентарь, характеристики, отношения, квесты | Сохранение тайтла | — |

- Тайтл влияет на глобальный прогресс только эффектами `global.xp`, `achievement` и `collect`.
- Глобальный прогресс доступен тайтлу только для чтения в условиях (`global.level`). Так можно делать награды между тайтлами: например, уровень аккаунта 5 открывает бонусную сцену.
- Описание платформенного уровня (кривая опыта, общие достижения, награды за уровни) — отдельный раздел студии «Платформа».
- **Энергия у каждого тайтла своя.** Балансы тайтлов не зависят друг от друга, а когда энергия кончилась в одном тайтле, игрок может перейти в другой, а не уйти с платформы.

## 5. Формат сцен (ink)

### 5.1 Пример
```ink
EXTERNAL affection(who)
EXTERNAL has(item)
EXTERNAL flag(name)

=== anna_gym_meet ===
# bg: gym
# music: upbeat
# show: anna neutral left
anna: Опять ты? Я начинаю думать, что это не совпадение.
# effect: flag met_anna

{ has("water_bottle"):
    * [Предложить воду]
        # effect: take water_bottle
        # effect: affection anna +3
        # show: anna happy
        anna: О, спасибо. Ты внимательный.
}
* [Пошутить про тренера]
    # effect: affection anna +1
    anna: Ха. Только не при нём.
* { affection("anna") >= 20 } [Позвать на кофе] # premium: 15
    # effect: affection anna +5
    # effect: start_quest anna_coffee
    anna: …Давай. Но платишь ты.
- -> END
```

### 5.2 Конвенции
| Конструкция | Пример | Смысл |
|---|---|---|
| Реплика | `anna: текст` | Говорит персонаж из реестра тайтла |
| Реплика героя | `me: текст` | Протагонист |
| Строка без префикса | `Зал был почти пуст.` | Повествование |
| `# bg`, `# show`, `# hide`, `# music`, `# sfx`, `# wait`, `# fx` | `# show: anna smirk left` | Сцена: фон, персонажи, звук, паузы, эффекты |
| `# effect: <операция> ...` | `# effect: affection anna +3` | Изменение состояния игры, применяется сервером в конце сцены |
| `# premium: <цена>` на выборе | `* [...] # premium: 15` | Платный выбор: списание кристаллов через сервер в момент выбора |
| `EXTERNAL` функции | `affection("anna")`, `has("rose")`, `flag("met_anna")`, `stat("charm")`, `global_level()` | Чтение состояния игры |

### 5.3 Контракт сцены и движка
- На входе сцена получает снимок состояния. `EXTERNAL`-функции читают его с учётом эффектов, накопленных в этой же сцене: после `take water_bottle` вызов `has("water_bottle")` уже вернёт ложь.
- Эффекты задаются только тегами со статическими значениями. Поэтому компилятор извлекает из сцены полный белый список, а сервер не примет эффект, которого в сцене нет.
- В превью и песочнице студии `EXTERNAL`-функции читают состояние песочницы.

### 5.4 Линтер в студии
- Ошибки компилятора ink.
- Неизвестные ключи: персонажи, эмоции, фоны, звуки, а также предметы, флаги, квесты и характеристики в эффектах и `EXTERNAL`-вызовах.
- Набор выборов, где все варианты платные.
- Сцена, которую не запускает ни одно событие, занятие или квест (предупреждение).
- Недостижимые узлы и висящие переходы.

## 6. Хранение ассетов

### 6.1 Что где лежит
| Что | Где | Доступ |
|---|---|---|
| Исходники (PNG, WAV) | Supabase Storage, `originals` | Приватный |
| Оптимизированные варианты (WebP, m4a) | Supabase Storage, `assets` | Приватный, источник для локальной копии |
| Копия вариантов | Диск VPS, `/srv/assets` | Раздаёт Caddy по `/assets/...`, кэш навсегда |
| Бэкапы базы и копия `originals` | S3 в РФ, `backups` | Персональные данные не покидают РФ |
| Скомпилированные сцены и данные тайтла | PostgreSQL (сборки), отдаёт API | С проверкой доступа |
| Графика интерфейса платформы | git, бандл Vite | — |

### 6.2 Ключ отдельно от файла
- Данные и сцены ссылаются на ключ: `# bg: gym`, `location.background: gym`.
- Ключ указывает на текущую версию ассета, а у версии есть файлы с хешем в имени: `a/3f/3fa9c2e1…b7.1080.webp`.
- Файлы не перезаписываются и кэшируются навсегда.
- Сборка фиксирует конкретные хеши, поэтому откат возвращает и старый арт.

### 6.3 Загрузка
1. Студия получает presigned URL и грузит исходник напрямую в `originals`.
2. `POST /api/studio/assets/:id/confirm` — проверка формата, веса и размеров. У спрайтов одного персонажа должен быть единый холст.
3. Задача procrastinate: Pillow для картинок, `ffmpeg` для звука.
4. Варианты кладутся в `assets` и в `/srv/assets`.

Если прямая загрузка в Supabase у команды сбоит, студия грузит через API. Массовая загрузка с разбором имён: `bg_gym.png` → фон `gym`, `anna_smirk.png` → эмоция `smirk` персонажа `anna`, `item_rose.png` → иконка предмета `rose`.

### 6.4 Форматы и размеры
| Тип | Что генерируем | Ориентир по весу |
|---|---|---|
| Фон (сцены и локации) | WebP q≈80, 1080×1920 и 720×1280 | ≤ 400 КБ |
| Спрайт | WebP с альфой, единый холст на персонажа, 2 размера | ≤ 300 КБ |
| Иконка предмета | WebP 256×256 | ≤ 30 КБ |
| Обложка тайтла | WebP 600×800 + превью для каталога | ≤ 150 КБ |
| Музыка | AAC `.m4a` 96–128 кбит/с | 1–3 МБ |
| Звуки | AAC `.m4a` или MP3 | ≤ 100 КБ |

### 6.5 Объёмы и CDN
- **Предзагрузка по кусочкам:** при входе в тайтл грузится оболочка тайтла (карта, иконки, интерфейс). Фон локации грузится при переходе, ассеты сцены — перед её запуском. Ассеты, которые понадобятся следующими, плеер подгружает заранее в фоне.
- **Трафик** при тех же 10 тысячах игроков в день — порядка единиц ТБ в месяц. Пока его отдаёт VPS: канал 100 Мбит/с — на несколько тысяч игроков в день, 1 Гбит/с — на десятки тысяч.
- **Когда подключать CDN:** растёт время загрузки сцен в вечерние часы или канал в пике загружен больше чем наполовину. CDN берём российский, источник — наш VPS.

### 6.6 Бэкапы и удаление
- В S3 Supabase нет версионирования, поэтому ночной `rclone sync` бакета `originals` в российский `backups` обязателен. В MVP ничего не удаляем.
- `assets` и `/srv/assets` восстанавливаются из `originals` и `assets` соответственно.

## 8. Студия (MVP)

1. **Вход:** Login Widget или ссылка из бота. Роли: `admin`, `designer` (данные и баланс), `writer` (сцены).
2. **Тайтлы:** список, настройки, обложка, порядок в каталоге, статус.
3. **Ассеты и персонажи:** библиотека с массовой загрузкой; персонажи с эмоциями, проверка единого холста.
4. **Игровые данные:** формы, которые генерируются из схем.
   - Выпадающие списки вместо ручного ввода ключей: предметы, локации, сцены, квесты.
   - Ошибки ссылок видны сразу при сохранении.
   - Импорт и экспорт CSV для табличных данных (кривые, цены, эффекты занятий): геймдизайнеру удобнее считать баланс в таблице.
5. **Сцены:** CodeMirror 6, подсветка ink, автодополнение ключей ассетов и игровых данных, линтер из §5.4. Превью рядом с кодом:
   - «играть отсюда»;
   - выбор стартового состояния;
   - переход от реплики к строке.
6. **Песочница:** тайтл целиком в рамке 9:16, тот же `game-ui`, что в плеере.
   - Старт с любого состояния: готовые пресеты («день 5, симпатия Анны 25») или ручная правка.
   - Панель отладки: перемотка времени, ресурсы, выдача предметов, этап квеста, лог действий.
   - Та же песочница открывается на телефоне по превью-ссылке, только у пользователей из `staff`.
7. **Симулятор баланса:** прогоняет N виртуальных игроков с выбранными стратегиями на D дней на том же движке. Отчёт показывает:
   - в какой день и где игроки упираются в энергию;
   - когда открываются квесты и сцены;
   - уровень и ресурсы по дням;
   - сцены, до которых никто не дошёл.
8. **Карта связей** (только чтение): какие события, занятия и квесты ведут к каким сценам.
9. **Публикация:** серверная проверка (схемы, ссылки, белые списки эффектов, сохранность идентификаторов), заметка к версии, откат в один клик.
10. **Платформа:** кривая уровня аккаунта, общие достижения, награды за уровни.

## 9. Плеер — Telegram Mini App (MVP)

**Экраны платформы:** каталог тайтлов → карточка тайтла («Начать» или «Продолжить») → профиль (уровень, достижения, коллекция).

**Экраны тайтла** (пакет `game-ui`, интерфейс строится по конфигурации тайтла):
- **Хаб/карта:** локации, кто где сейчас находится, заблокированные места с причиной.
- **Панель сверху:** день, слот времени, ресурсы из конфигурации (энергия с таймером восстановления, деньги).
- **Локация:** фон, присутствующие персонажи, занятия с ценой и эффектами, подтверждение действия.
- **Сцена:** `vn-renderer`.
- **Инвентарь:** предметы, «подарить», «использовать».
- **Журнал квестов**, экран отношений, экран характеристик.
- **Конец дня:** сводка изменений.

Каждое действие показывает сводку изменений («+3 к форме, −20 энергии»). Без неё игрок не видит, как работает механика.

**Интеграция с Telegram:**
- `Authorization: tma <initDataRaw>` в каждом запросе.
- Полноэкранный режим, портретная ориентация, safe area, `disableVerticalSwipes()`.
- `BackButton` связан с навигацией, хаптики на действиях и выборах.
- Диплинки `startapp=title_<slug>` и `preview_<token>`.
- Музыка — после первого тапа.

**Аналитика:**
- **Платформа:** `app_open`, `title_open`, переходы между тайтлами.
- **Тайтл:** действия по типам, расход энергии, игровой день и момент ухода, сработавшие события, выборы в сценах, прохождение квестов.
- **Технические метрики:** время загрузки, `asset_load_failed`.

## 10. Инфраструктура и деплой

Основа сделана на этапе 0 и описана в [docs/SETUP.md](SETUP.md). Ниже — принятые решения.

### 10.1 Окружения
| | Локально | Стейджинг | Прод |
|---|---|---|---|
| Кто пользуется | Разработчик | Команда | Игроки и команда (прод-студия) |
| Бот | Личный dev-бот | `@<name>_staging_bot` | `@<name>_bot` |
| Домены | `localhost` | `staging.<домен>`, `studio-staging.<домен>` | `app.<домен>`, `studio.<домен>` |
| База | Postgres в Docker | Своя, на том же VPS | Своя |
| Файлы | Локальный S3 в Docker (с этапа 3) | Отдельный проект Supabase (Free) | Проект Supabase (Free на MVP, Pro позже) |
| Обновляется | Постоянно | При мердже в `develop` | При мердже `develop` → `master`, после подтверждения |

- **У стейджинга своё всё:** бот, база, бакеты, ключи.
- **На MVP хватит бесплатного Supabase.** Опубликованный контент раздаётся из локальной копии, поэтому засыпание проекта мешает только загрузке нового арта. Pro понадобится, когда исходники приблизятся к 1 ГБ; он оплачивается иностранной картой.

### 10.2 Путь контента
- Команда работает в прод-студии. Черновики, неактивированные сборки и песочница игрокам не видны.
- Стейджинг нужен для проверки кода. Контент там — демо-тайтл из сидов.

### 10.3 Состав на сервере
- `edge` — Caddy на 80/443, TLS и домены окружений.
- На каждое окружение:
  - `web` — Caddy со статикой, `/assets` и прокси в API;
  - `api`;
  - `worker` (с этапа 3);
  - `db`.
- `deploy.sh` выполняет миграции, `up --wait` и регистрирует домен окружения в edge.

### 10.4 Настройка Supabase (только Storage)
- **Включить:** S3-протокол и ключ (только в env API); бакеты `assets` и `originals` — приватные, на `assets` лимит размера и разрешённые типы; ни одной политики на `storage.objects`.
- **Выключить:** Data API, все способы входа и регистрацию, Image Transformations. Edge Functions не деплоить.
- **Проверить на сервере:** `python -m storymaker_api.doctor`.

### 10.5 Ветки и пайплайн
- **Ветки:**
  - `master` — прод;
  - `develop` — стейджинг;
  - фичи — от `develop` и обратно через PR;
  - релиз — PR из `develop` в `master`.
- **PR → CI:** ruff, pyright, pytest (включая тесты движка и симулятора на демо-тайтле), eslint, prettier, tsc, vitest, сборка.
- **Merge в `develop`** → образы в GHCR → выкатка на стейджинг. **Merge в `master`** → то же для прода после подтверждения.

### 10.6 Надёжность
- Ночной `pg_dump` и `rclone sync` бакета `originals` в российский бакет `backups`. Восстановление проверяем руками до запуска.
- Sentry без персональных данных, uptime-пинг, структурные логи.
- Секреты — в GitHub Environments и `.env` на сервере.

### 10.7 Где хоститься
- VPS и S3 для бэкапов — у российского провайдера (Selectel, Timeweb Cloud, Yandex Cloud), канал от 100 Мбит/с, лучше 1 Гбит/с.
- Supabase — Франкфурт, только арт и звук.

## 12. Параллельный трек: контент и геймдизайн

Для dating sim нужны три роли: сценарист (сцены), художник (арт) и **геймдизайнер** (данные, баланс, квесты). Геймдизайнер в команде есть; кто пишет сцены и рисует арт — открытый вопрос §15.

- **До студии** геймдизайнер ведёт данные тайтла в файлах YAML/CSV по схемам движка. С ≈ 6-й недели он проверяет их симулятором баланса.

- **Недели 1–2:**
  - концепт первого тайтла, механики и их числа на бумаге;
  - арт-спецификация (вертикаль 9:16, фон 1080×1920, единый холст спрайтов, список эмоций, иконки предметов 256×256), схема имён файлов;
  - синопсис и список сцен.
- **Недели 3–10:**
  - сцены в Inky;
  - таблицы баланса и данные (до готовности студии — в таблицах);
  - арт: 8–12 фонов, 2–4 персонажа × 5–6 эмоций, 10–15 иконок, музыка и звуки.
- **С этапа 4:** перенос в студию, проверка в песочнице, проходы симулятора. Всё, что неудобно команде, превращается в задачи для студии.

## 13. После MVP

### 13.1 Экономика на Telegram Stars — 2–3 недели
**Модель (гипотеза, решаем после MVP):** кристаллы общие для платформы, покупаются пачками за Stars. Тратятся на восполнение энергии, платные выборы, премиум-предметы и наряды. Позже — подписка.

**Флоу покупки:**
1. Клиент: `POST /api/purchases {productId}` → сервер создаёт `purchase(status=pending)` и вызывает `create_invoice_link` (валюта `XTR`, `payload = purchase.id`).
2. Клиент: `Telegram.WebApp.openInvoice(link, callback)`.
3. Бот получает `pre_checkout_query`. Сервер проверяет покупку и **в течение 10 секунд** отвечает `answer_pre_checkout_query`.
4. `successful_payment` → в одной транзакции: `purchase → paid` (уникальность по `telegram_payment_charge_id`), запись в `ledger`, обновление `wallets`.
5. Клиент перезапрашивает баланс.

**Траты** проходят через тот же цикл действия (§4.4) с `request_id`. Баланс никогда не меняется в обход леджера.

**Обязательно:**
- команда `/paysupport`;
- возвраты через `refund_star_payment` + обратная запись в леджере;
- оферта и политика конфиденциальности;
- админка: покупки и леджер пользователя, ручное начисление с комментарием.

**Деньги для бизнеса:** Stars выводятся через Fragment в TON, с задержкой (по открытым источникам — около 21 дня) и порогом. Юнит-экономику считаем по актуальным условиям до назначения цен.

### 13.2 Удержание и рост
- Уведомления через бота: «энергия восстановилась», «вышел новый тайтл». Нужен `requestWriteAccess`, если игрок пришёл по прямой ссылке.
- Ежедневные награды на уровне платформы.
- Рефералка через `startapp=ref_<id>`, шаринг через `shareMessage` и `shareToStory`.

### 13.3 Глубина
- Магазины, гардероб со слоёными спрайтами, платные наряды.
- Мини-игры как плагины `game-ui` с регистрацией по ключу.
- Механики симуляторов вроде «Тюряги» (авторитет, распорядок, конфликты) — расширения движка, доступные всем тайтлам.
- Локализация.

## 14. Риски

| Риск | Последствие | Что делаем |
|---|---|---|
| Объём кода (~19 недель) | Поздний запуск | Вертикальный срез; режем механики первого тайтла, а не инструменты; два трека разработки |
| Каждый тайтл хочет уникальных механик | Движок обрастает частными случаями | Механика добавляется в движок как общая возможность; мини-игры — плагины |
| Баланс не сходится | Игроки упираются в энергию или проходят всё за день | Симулятор на том же движке, аналитика расхода энергии и ухода по игровым дням |
| Правки опубликованного тайтла ломают сохранения | Игроки теряют прогресс | Стабильные идентификаторы, проверка при сборке, правила миграции |
| Накрутка ресурсов | Потери на монетизации | Всё на сервере; эффекты сцен по белому списку; `request_id` против повторов |
| Нет геймдизайнера | Студия есть, тайтла нет | Роль в команде с первой недели |
| Контент, особенно арт, не успевает | Нечего показать на бете | Трек контента с недели 1 |
| Покупка Stars в РФ затруднена | Низкая конверсия | Проверить, как ЦА покупает Stars, до построения экономики |
| Комиссии и курс вывода Stars → TON | Маржа ниже ожидаемой | Юнит-экономика по актуальным условиям |
| Правила Telegram и магазинов к контенту | Блокировка | Рейтинг 16+, без откровенного контента, только Stars |
| Supabase или Cloudflare тормозят в РФ | Команда не может загрузить арт | Игроки получают ассеты с VPS; переезд на российский S3 — `rclone` + env |
| Канал VPS не тянет пик | Медленная загрузка | Метрики загрузки; CDN сменой `ASSETS_BASE_URL` |
| Нет версионирования в Supabase S3 | Удаление исходников необратимо | Ничего не удаляем; ночной `rclone sync` в `backups` |
| 152-ФЗ, юрлицо, налоги с дохода в TON | Юридические риски | Персональные данные только в РФ; юрист до монетизации |

## 15. Решения

### Приняты
- Платформа: один бот — сборник тайтлов, тайтлы запускаются внутри него; общий аккаунт и глобальный прогресс.
- Тайтлы — dating sim: игровой цикл исполняет сервер по данным тайтла, сцены — клиент.
- Один движок на все тайтлы, настройка данными; схемы — на Pydantic.
- Сцены — ink + теги; эффекты по белому списку.
- Python — сервер и движок; TypeScript — сцены, плеер, студия.
- Аудитория в РФ: VPS, база, бэкапы — в России; Supabase — только арт и звук, раздаёт VPS.
- Студия — отдельный сайт с входом через Telegram; RLS не используем.
- Ветки: `master` — прод, `develop` — стейджинг, фичи — через PR в `develop`.
- Первый тайтл: игровые слоты времени, энергия восстанавливается в реальном времени и восполняется за кристаллы.
- Энергия у каждого тайтла своя.
- Команда: один разработчик и геймдизайнер; срок ~19 недель.
- Монетизация (что продаём за Stars) — после MVP.

### Открытые вопросы
1. **Состав глобального прогресса** (§4.6):
   - общий кошелёк;
   - уровень и опыт аккаунта;
   - достижения;
   - коллекция.

   Какие из них нужны в MVP и нужны ли награды между тайтлами? *Рекомендация:* в MVP — уровень с опытом и достижения. Коллекция — если в тайтле будут отдельные иллюстрации. Кошелёк — вместе с монетизацией, но кристаллы сразу считаем общими для платформы.
2. **Сценарист и художник:** кто пишет сцены и рисует арт? Готов ли сценарист к текстовому формату ink с подсказками и превью?
3. **Название проекта, бота и домен.**
4. **Провайдер в РФ** для VPS и бэкапов: Selectel, Timeweb Cloud или Yandex Cloud.
